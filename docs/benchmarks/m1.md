The 1M-chunk run uses the fake embedder (deterministic hashed vectors, no model): embedding 1M
chunks with the real model takes over two hours here, and the fake embedder's 384-dimension
vectors cost the same in the index, so search and storage behave the same. The real model's
own cost is measured at 100k and added for the 1M projection.

## Method

`alice bench` builds a throw-away `ALICE_HOME` (a temporary directory, or `--dir` to keep it and
reuse the data in a later run). It never touches the user's data; with `--real` it only reads
the model from `~/.alice/models`.

- **Corpus** (deterministic): each memory is a sentence of 8–27 words, each chunk two such
  sentences plus one *raw-only* word. Each word is, with probability 2/7, one of 20 common
  English tech words; 1/7 one of 10 Thai words; 1/7 one of 5 code identifiers
  (`HostLinkReconnect`, `internal/teacher/jev/client.go`, …); 3/7 one of 2,000 made-up words.
  Raw-only words (500 made-up ones, one per chunk) never appear in a memory. One chunk in 50
  also holds one of 10 rare Thai words (`สัญญาเช่าบ้าน`, …) and one in 50 one of 10 rare
  identifiers made of common words (`lease_token_frame`, …), each in about 0.2% of chunks (2,000
  at 1M): rare, but in many more chunks than one list returns. The common words are
  deliberately dense, each in 25–45% of all chunks: the worst case for ranked full-text search.
- **Load:** chunks in ingest requests of 1,000, then memories (64 concurrent `remember`s), then
  wait until the embedding backlog is empty and the index is ready. While waiting, one recall
  every 250 ms measures search while the worker embeds.
- **Latency:** 200 rounds, one call at a time, in process through the service layer that the
  HTTP API and MCP use (no HTTP hop): `remember` of a new memory; `recall` of a three-word query
  (knowledge tier, the default); the same query with `include_raw`, and with `include_raw`
  under a date filter that keeps everything (filtered lists read 400 candidates instead of 100);
  `include_raw` for a rare Thai word beside a common one, and for a rare identifier beside a
  common word; a query of two raw-only words (no memory matches, so recall takes the raw
  fallback); `context`.
- **`get_by_seqs`:** 50 calls each with 500 and 2,000 random memory seqs (one recall passes up
  to 500 memory candidates, up to 2,000 with filters).
- **Start-up parts:** after the service stops, each step `Service::start` and the writer take,
  timed on its own: open + migrate, the newest-HLC scan, `embeddings::count`, vector index
  open, and a full index rebuild (what happens when the index is missing or stale).
- **Daemon:** a real `alice daemon run` child on the same data: time until it answers a
  verified ping, then four bursts of 64 concurrent recalls over HTTP (a third each knowledge,
  `include_raw` and fallback queries), with RSS and physical footprint after start, after the
  bursts, and the peak. RSS counts resident pages only: under memory pressure macOS compresses
  idle pages and RSS drops without anything being freed. The physical footprint (macOS, what
  Activity Monitor shows) also counts compressed memory, so it moves less, though compression
  still lowers it; the peak values are the most robust.

## What this task changed, before and after

"Before" is the first measurement of each row in this task, taken before the change the row
names (the raw-list and reader rows on the code of `c0991e2`); "after" is `e435bf4`, except the
`get_by_seqs` row (build of `bc557b4`; the function has not changed since).

| Measurement | Before | After | Change |
|---|---|---|---|
| `recall` `include_raw` p50 / p95, 1M chunks | 449 / 947 ms | 40 / 166 ms | Raw-tier lists read each term up to its own share of a 5,000-row budget (see below) |
| Raw fallback p50 / p95, 1M chunks | 70 / 128 ms | 33 / 89 ms | same |
| Daemon peak RSS, 1M chunks (64-recall bursts) | 3,301 MB | 860 MB | Reader pool capped at 8 connections (64 concurrent recalls opened 64); no SQLite `mmap`; 16 MiB reader caches |
| Burst recalls that timed out (5 s), 1M chunks | 89 of 256 | 0 | same |
| Daemon peak RSS, 100k chunks, fake embedder | 517 MB | 170 MB | same |
| Daemon footprint after start / peak, 100k chunks, real model | 1,037 / 1,263 MB | 691 / 847 MB | One shared model instance instead of two; embedding batches of at most 1,024 tokens counted by the model's tokenizer |
| `get_by_seqs`, 25,000 memories, 500 / 2,000 seqs (p50) | 1.75 / 16.0 ms | 1.08 / 3.87 ms | Position map instead of a linear search per sort comparison; topics read in one query |

How the raw ranking got here (1M chunks, include_raw p95): `3de35db` ranked among the newest
5,000 matches of all the query's terms together (172 ms), which let a common term push an older
chunk with a rarer term out of the lists (review finding I1). `ef59474` / `94c63c4` split rare
from common terms (238 / 185 ms) but still let common terms share one window, and the trigram
list measured rarity only up to k (fix round 2). `01340fb` gave every common term its own share
and the trigram list shares up to the window; its first 1M run, with the new rare Thai and
identifier queries, missed the budget for identifiers (p95 303 ms). `e8390f9` ranked every term
in one query within its share (no count pass, no second pass for rare terms) and read ASCII
trigram terms only to k (include_raw 201 ms, identifiers 160 ms), and `13a4189` stopped searching
`_` identifiers as phrases in the word list (156 ms; identifiers 112 ms). The next review found
that each term kept only its own top k before the sum, losing chunks with every query word, and
that qualified forms of an identifier (`self.lease_token_frame`, `LEASE_TOKEN_FRAME_LIMIT`, ...)
no longer matched it (N1, N2); `18e1511` sums every row read and indexes the joined names
(include_raw 182 ms, rare Thai 112 ms at load ~11), and `e435bf4` leaves words unicode61 splits
(Thai at combining marks) to the trigram list (166 ms; rare Thai 41 ms; filtered 160 ms).

**Why the raw lists were slow, and what they guarantee now.** FTS5 computes BM25 for every row
that matches before it can return the best 100. A common word that appears in 40% of 1M chunks
cost ~320 ms per list (`unicode61`), and a Thai word ~400 ms (`trigram`, where every match is a
phrase of trigrams). Now:

- **Word and identifier lists.** Every term that has a match gets its **own share** of the
  budget, max(k, 5,000 / number of such terms) rows, and reads its newest matches up to that
  share (FTS5 reads newest first and stops there); k is 100, or 400 with filters. A chunk scores
  the sum of the BM25 parts of every term that read it (every row read counts, so a chunk with
  all the query's words is never lost below each word's own top k), and the best k are kept.
  Rows read per list are at most max(5,000, terms × k): 5,000 for a few terms, up to 6,400 for
  the word list's 64 terms (32 words, 32 variants), or 25,600 with filters.
- **Identifiers.** The raw word list does not search identifiers holding `_` as phrases of
  their words: BM25's IDF for a phrase of common words reads every match of each word with
  positions, 36–50 ms per identifier at 1M chunks. The identifier list finds them as one token
  in every written form: each name in an indexed token also yields the joined runs of its
  words, so `self.lease_token_frame`, `store/lease_token_frame.rs`,
  `crate::daemon::lease_token_frame()`, `LEASE_TOKEN_FRAME_LIMIT`, `lease-token-frame` and
  `LeaseTokenFrame` all carry `leasetokenframe`; their words stay in the word list.
- **Trigram list.** A non-ASCII term (Thai, CJK, ...), for which this is the main lexical list,
  reads its newest max(k, 5,000 / number of non-ASCII terms) matches; an ASCII term reads its
  newest k substring matches (as a whole word it has its share in the word list, as an
  identifier in the identifier list). A chunk scores Σ 1 / (each matching term's count, capped
  at what it read); ties are taken term by term, so two terms past their shares share the list.
  Not BM25: its IDF needs every match of each trigram phrase (60–90 ms at 1M even when bounded).
- **Guarantee.** No term can crowd another out of the raw tier: each is read up to its own
  share. A term with at most its share of matches is ranked over all of them; matches beyond a
  term's share, and an ASCII term's substring-only matches beyond its newest k, are not read
  (newest first), so recall for very common terms is not exhaustive. The vector list still ranks
  every chunk by meaning.
- **Cost.** A share costs ~5–16 ms at 1M chunks for a single word. Words unicode61 splits at
  combining marks would also be phrases of common fragments in the word list (half of the
  bench's common Thai words: `ตัดสินใจ` becomes `ต`, `ดส`, `นใจ`; 25–31 ms of IDF reading each),
  so they are left to the trigram list, which searches them whole with their own share. Phrase
  terms are left only for rare punctuation inside a word. The bench times rare Thai words, rare
  identifiers and a filtered query separately.

**Why the daemon used gigabytes.** The reader pool kept 8 idle connections but opened a new one
for every concurrent request beyond that, each with a 64 MiB page cache and a 256 MB memory map
of the database (each map's touched pages count toward RSS separately). Reads through the OS file
cache measured the same speed as the memory map, so the map is gone and the pool is a hard cap.

## Memory

Measured parts of the daemon's memory (physical footprint):

| Part | Size | Notes |
|---|---|---|
| Vector index, 1M chunks | ~560 MB | int8 HNSW in RAM: 384 B per vector plus ~130 B of graph |
| Embedding model, one instance | ~600 MB | tokenizer of the 250k-token multilingual vocabulary ~250 MB (HF `tokenizers` Unigram), ONNX session ~265 MB, plus allocator slack |
| ONNX Runtime working memory | +100 MB with 1,024-token batches | it keeps the size of its largest call: one batch of 32 texts of 512 tokens added 1.4 GB |
| SQLite | ≤ 192 MB | writer 64 MiB cache, 8 readers × 16 MiB |

Before this task the daemon held two model instances (worker and queries); with long transcript
chunks each could grow by 1.4 GB. One shared instance with batches of at most 1,024 padded tokens
(counted with the model's own tokenizer: a characters/3 estimate undercounted identifiers, JSON
and hex ids by up to 2x) saves ~600 MB and caps the growth; a query waits for one worker batch
at most (recall p95 while embedding: 58.8 ms at 100k in the 13a4189 run; 146 ms in the e435bf4
run at load 25–35).

**The 800 MB budget at 1M chunks is missed**, even without the model: the fake 1M daemon held
666–784 MB RSS (footprint 773–862 MB) and peaked at 860 MB RSS. With the local model,
projected by adding the model's share at 100k (real minus fake run): RSS ≈ 666–784 + 660 (after
start) ≈ 1.4 GB steady and ≈ 860 + 740 (peaks) ≈ 1.6 GB at peak, ≈1.7 GB with the 13a4189 run's
share; physical footprint ≈ 1.4–1.5 GB steady and ≈ 1.55 GB at peak. At 100k with the model the
daemon peaked at 910 MB RSS (847 MB footprint; 1,003 MB RSS in the 13a4189 run). The model
alone is three quarters of the budget. Ways to close the gap, for M2: a compact SentencePiece
tokenizer instead of the HF Unigram trie (~250 MB → tens of MB); keep the chunk vectors of a
saved index memory-mapped (usearch `view`) with a small in-memory index for new chunks, so they
cost page cache rather than footprint (~450 MB at 1M); or binary-quantise the raw tier's
vectors (48 B instead of 384 B each). An HTTP embedding provider (M2) removes the model from the
daemon.

## Start-up

- **Open + migrate, newest HLC:** milliseconds at any size.
- **`embeddings::count`:** a covering-index scan of the `embeddings` primary key: 25 ms with a
  warm OS cache at 1M, 0.5–0.9 s cold (the index pages are spread through the 2.7 GB file).
- **Index open:** 279–667 ms at 1M (513 MB read; the slower figures under load).
- **Index rebuild:** 325–420 s at 1M on one thread (14–24 s at 100k). It only runs when the index
  files are missing, damaged or out of date; meanwhile search uses the word lists only. A
  parallel rebuild is an obvious improvement.
- **Daemon ready:** 65–134 ms at 100k with the fake embedder; 576–791 ms with the model; 0.5–1.7 s
  at 1M (the count and the index read). `alice status` at 1M takes about a second cold: health
  counts 1M chunk rows.

## Search quality with the real model

`crates/alice-embed/tests/real_search_quality.rs` (ignored; reads the model from
`~/.alice/models`) loads the 10 gold memories and 13 gold queries of
`crates/alice-core/tests/fixtures/search_gold.jsonl`, plus six unrelated queries (food, sport,
travel, gardening, gold prices; Thai and English), each answered by one raw chunk.

- **Ranking:** every gold query ranks its memory first: MRR 1.000, 13 of 13 in the top 3 (every
  gold query also has a word or identifier match, so the vector side adds to a lexical hit).
- **Similarity** (query vs memory, as the int8 index reports it; exact cosine is ~0.01 higher):

  | Pairs | n | min | median | max |
  |---|---|---|---|---|
  | gold query vs its memory | 13 | 0.841 | 0.872 | 0.904 |
  | gold query vs the other gold memories | 117 | 0.708 | 0.765 | 0.829 |
  | unrelated query vs gold memories | 60 | 0.670 | 0.730 | 0.771 |

- **`relevance_floor`:** the sweep covers 0.75 to 0.95 in steps of 0.01. Every value in it keeps
  all 13 gold queries in the top 3 (MRR 1.000) and lets the raw fallback fire for all six
  unrelated queries; below 0.78 some unrelated pairs reach the floor (5 of 60 at 0.75), but never
  three for one query, so the fallback still fires. At 0.82 all 13 gold pairs count as
  relevant on similarity alone (the weakest is 0.021 above the floor), 2 of 117 neighbouring
  pairs do, and no unrelated pair does (the strongest is 0.049 below). 0.83 would exclude the
  two neighbours but leave the weakest gold pair only 0.011 above the floor. **0.82 was already
  right and is kept**; the test now asserts that every gold pair is at or above the floor and
  every unrelated pair below it.
- Made-up words behave differently: in the real-model bench, two-word queries of made-up
  raw-only words reached 0.82 against three or more synthetic (word-salad) memories, so the
  fallback fired for only 10 of 200. Nonsense strings sit close together in e5's
  space; real text does not (unrelated pairs above, 0.67–0.77).

## Surprises

- The embedding model, not the data, dominates memory: one loaded instance is ~600 MB, and the
  HF tokenizer for the 250k-token multilingual vocabulary is ~250 MB of that. ONNX Runtime keeps
  the working memory of its largest call, so a single batch of 32 long transcript chunks used to
  add 1.4 GB for the life of the daemon.
- Ranking cost in FTS5 follows how many rows match, not the `LIMIT`: on a dense corpus a
  three-word query touched most of 1M chunks. Even with ranking bounded, BM25's IDF still counts
  every match once, which is cheap for words and expensive for trigram phrases. And a cheap fix
  (one window over all terms) silently hid rare terms behind common ones.
- A reader pool that only capped *idle* connections let a burst of 64 recalls open 64
  connections, each mapping 256 MB of the database: 3.3 GB RSS.
- RSS on a busy Mac is a moving target: idle pages of the daemon (the vector index) were
  compressed within seconds, and RSS fell by hundreds of MB without anything being freed. The
  physical footprint is reported next to RSS for that reason.
