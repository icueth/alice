# M3 benchmarks (import and compatibility)

Numbers are filled in by Task 19. This page holds what Task 16 measured.

## Import under load

Test: `crates/alice-daemon/tests/import_concurrency.rs`, release build, fake embedder, synthetic palace
(`fixture::synthetic_palace`: 600-900 character chunks, 3% knowledge drawers, 5% repeats), 20 clients that
each loop `remember` (unique text) + `recall` (alternating a client memory and a rare word of the palace)
with a 5 ms pause, until the import ends. Machine: 14 cores, shared with other work, run at `nice -n 15`.
Budgets: remember p95 < 50 ms, recall p95 < 200 ms.

```
ALICE_TEST_BULK=20000  : import 20000 drawers in 30.7s; remember p95 39.9 ms, recall p95 120.7 ms (7566 remembers, 7566 recalls)
ALICE_TEST_BULK=30000  : import 30000 drawers in 44.6s; remember p95 41.7 ms, recall p95 144.2 ms (9604 remembers, 9604 recalls)
ALICE_TEST_BULK=100000 : import 100000 drawers in 144.9s; remember p95 47.0 ms, recall p95 282.2 ms (19643 remembers, 19643 recalls)   <- recall over budget
```

The same 20 clients on the 100,000-drawer database with no import running: remember p95 10.4 ms,
recall p95 128.2 ms. So the 100k recall figure is the import's doing (the import took 49 s alone and 145 s
under load). At the end of the 30k run the write-ahead log was 744 MB: 20 clients always have a reader open,
so SQLite never gets the quiet moment it needs to restart the log. This is the likely cause and has not been
confirmed; the fix would be in the store's checkpoint policy (M2), so it was not changed here.

One-batch test (`one_batch_never_holds_the_writer_longer_than_the_slice_budget`, 100,000 drawers, a probe
`remember` every 5 ms): 4781 probes, longest ack 37.1 ms (budget 150 ms); 6786 batches, largest 200 records
(a `collapsed` batch, which carries no text) and 15,488 bytes of text.

What was changed to get there: import batches close at 50 records or 16 KB (were 200 and 64 KB) and the job
pauses 2 ms after each committed batch. With 200/64 KB batches remember p95 was 65-82 ms at 30k-100k drawers.

## Fix round 1: write-ahead log control (import job only)

The M3-side WAL control the review asked for was built and measured. Live log = frames in use, from the
result of a `PASSIVE` checkpoint (the `-wal` file never shrinks when the log restarts, so its size cannot
say when pressure is gone); peak is taken at the job's checks (every 20 batches), "end" is the file size.

| variant | scale | import time | remember p95 | recall p95 | WAL live peak / file at end |
|---|---|---|---|---|---|
| none (round 0) | 30k | 44.6 s | 41.7 ms | 144.2 ms | - / 744 MB |
| PASSIVE every 20 batches + back-off 25 ms steps, 2 s cap, above 128 MB | 20k | 89 s | 26.7 ms | 218.8 ms (over) | 1756 MB / 4 MB |
| same | 30k | 122 s | 26.6 ms | 259.9 ms (over) | 2572 MB / 4 MB |
| PASSIVE only, no back-off (TRUNCATE at the end, later removed) | 20k | 31.5 s | 42.8 ms | 125.0 ms | 569 MB / 585 MB (3 runs: 569-818 peak) |
| same | 30k | 46.4 s | 44.4 ms | 153.4 ms | 1016 MB / 4 MB |
| same | 100k | 152.6 s | 50.3 ms (over) | 300.9 ms (over) | 4407 MB / 4 MB |
| batches 100 rec / 32 KB, pause 4 ms (tuning try) | 100k | 131.3 s | 60.3 ms (over) | 285.6 ms (over) | 3428 MB / 3456 MB |

Findings
- Backing off makes it worse: with 20 readers always open the log never gets a quiet moment, so waiting
  only lengthens the import, and the log grows with the clients' own commits and the embedding worker's
  for as long as the import lasts.
- A blocking `wal_checkpoint(RESTART)` from a second connection (which would restart the log) made the
  writer's own transactions fail with `database is locked` within seconds under load, so it is NOT used.
  An end-of-job `TRUNCATE` (3 s wait, then no wait) shrank the log (4 MB at the end of those runs) but also
  made writes issued right after the job fail with `database is locked` (7 compat_flow tests and one
  import_flow test failed in the full run), so it was removed too. The log is left as the clients leave it
  (e.g. 585 MB after a 20k run) until the store's own checkpointing, or a restart, shrinks it.
- The 100k miss stays: recall p95 about 300 ms against the 200 ms budget with 20 closed-loop clients, while the
  same clients on the finished 100k database (no import) measured 128 ms. Bigger batches did not help.
  The remaining lever is the store's checkpoint policy (`journal_size_limit` / `wal_autocheckpoint` / a
  periodic truncate in maintenance), which is M2 behaviour and was left alone.
