# M3 benchmarks (import and compatibility)

**After the M2 ranking and WAL fixes (merge 153cb45):** the write-ahead log is no longer the problem (100k: 310 MB at most against 4.4 GB before), but the 100k latency re-run was taken on a machine at load 13-14 and is not a clean comparison: remember p95 148 ms, recall p95 406 ms (both over budget; see "Re-check after M2"). Gold set: Alice 0.776 nDCG@10 against MemPalace 0.806, still short; the CI lexical test now passes. Details below.

**100k before the M2 fixes: MISS** (recall p95 ~300 ms vs the 200 ms budget with 20 constantly-reading clients; cause: unbounded WAL in the M2 store, inferred from the evidence below and not proven; needs an M2 checkpoint policy - escalated). 20k and 30k pass both budgets.

Numbers are filled in by Task 19. This page holds what Task 16 measured.

## Import under load

Test: `crates/alice-daemon/tests/import_concurrency.rs`, release build, fake embedder, synthetic palace
(`fixture::synthetic_palace`: 600-900 character chunks, 3% knowledge drawers, 5% repeats), 20 clients that
each loop `remember` (unique text) + `recall` (alternating a client memory and a rare word of the palace)
with a 5 ms pause, until the import ends. Machine: 14 cores, shared with other work, run at `nice -n 15`.
Budgets: remember p95 < 50 ms, recall p95 < 200 ms.

```
ALICE_TEST_BULK=20000  : import 20000 drawers in 30.7s; remember p95 39.9 ms, recall p95 120.7 ms (7566 remembers, 7566 recalls)
ALICE_TEST_BULK=30000  : import 30000 drawers in 44.6s; remember p95 41.7 ms, recall p95 144.2 ms (9604 remembers, 9604 recalls)
ALICE_TEST_BULK=100000 : import 100000 drawers in 144.9s; remember p95 47.0 ms, recall p95 282.2 ms (19643 remembers, 19643 recalls)   <- recall over budget
```

The same 20 clients on the 100,000-drawer database with no import running: remember p95 10.4 ms,
recall p95 128.2 ms. So the 100k recall figure is the import's doing (the import took 49 s alone and 145 s
under load). At the end of the 30k run the write-ahead log was 744 MB: 20 clients always have a reader open,
so SQLite never gets the quiet moment it needs to restart the log. This is the likely cause and has not been
confirmed; the fix would be in the store's checkpoint policy (M2), so it was not changed here.

One-batch test (`one_batch_never_holds_the_writer_longer_than_the_slice_budget`, 100,000 drawers, a probe
`remember` every 5 ms): 4781 probes, longest ack 37.1 ms (budget 150 ms); 6786 batches, largest 200 records
(a `collapsed` batch, which carries no text) and 15,488 bytes of text.

What was changed to get there: import batches close at 50 records or 16 KB (were 200 and 64 KB) and the job
pauses 2 ms after each committed batch. With 200/64 KB batches remember p95 was 65-82 ms at 30k-100k drawers.

## Fix round 1: write-ahead log control

Tried in the import job only (the M2 store is untouched). "WAL" below is the size of the `-wal` file
(`ImportStatus.max_wal_bytes`: largest size seen at the check made every 20 batches). Nothing in
the import job checkpoints now: the attempts gave no benefit, and the shipped build only measures.

Results of the attempts. Rows marked * had an end-of-job TRUNCATE or measured frames in use after a PASSIVE
checkpoint, which are not in the shipped build, so their WAL cells describe those experiments, not the shipped code.

| variant | scale | import time | remember p95 | recall p95 | WAL peak / end |
|---|---|---|---|---|---|
| none (round 0, 200 rec / 64 KB batches, no pause) | 30k | 44.6 s | 41.7 ms | 144.2 ms | - / 744 MB |
| PASSIVE every 20 batches + back-off (25 ms steps above 128 MB, 2 s cap) * | 20k | 89 s | 26.7 ms | 218.8 ms (over) | * / * |
| same * | 30k | 122 s | 26.6 ms | 259.9 ms (over) | * / * |
| PASSIVE only, no back-off * | 20k | 31.5 s | 42.8 ms | 125.0 ms | * / 585 MB |
| same * | 30k | 46.4 s | 44.4 ms | 153.4 ms | * / * |
| same * | 100k | 152.6 s | 50.3 ms (over) | 300.9 ms (over) | * / * |
| batches 100 rec / 32 KB, pause 4 ms (tuning try) * | 100k | 131.3 s | 60.3 ms (over) | 285.6 ms (over) | * / * |
| **shipped build** (50 rec / 16 KB, 2 ms pause, measure only) | 20k | 31.2 s | 41.4 ms | 118.0 ms | 533 MB / 546 MB |

Findings
- Checkpoint attempts gave no benefit: with PASSIVE the 100k recall was 300.9 ms against 282.2 ms before, and
  the log was as big or bigger. Backing off made it worse: with 20 readers always open the log never gets a quiet
  moment, so waiting only lengthens the import, and the log grows with the clients' own commits and the
  embedding worker's for as long as the import lasts.
- A blocking `wal_checkpoint(RESTART)` from a second connection made the M2 writer's own transactions fail
  with `database is locked` within seconds under load. An end-of-job `TRUNCATE` shrank the log but made writes
  issued right after the job fail (8 existing tests failed in a full run). Neither is used.
- The 100k miss stays: recall p95 about 300 ms against 200 ms, while the same clients on the finished 100k
  database with no import measured 128 ms. The no-import WAL size was not taken, so part of the log may come
  from the clients and the embed worker rather than the import. The cause (an unrestarted log under constant
  readers) is inferred; a direct proof would be the same run on a scratch build with `wal_autocheckpoint` or
  `journal_size_limit` set. That lever is the store's checkpoint policy (M2 behaviour), left alone.

## Re-check after M2 (Tasks 19/20 merged, HEAD 6c42c0e)

Same test, same command (`ALICE_TEST_BULK=100000 cargo test --release -p alice-daemon --test import_concurrency
twenty_clients -- --nocapture`), run once. The test panics on the remember budget, so it is reported FAILED.
The machine was busy with other work during the run (load average 13-14 on 14 cores: a mongoimport, OrbStack and
another test run), more than during the first measurement. A 20k control run straight afterwards, at the same load,
gave remember p95 68.3 ms and recall p95 154.0 ms against 39.9 / 120.7 ms in the first measurement, so about
1.3-1.7x of the latency difference is the machine. Latencies below are therefore pessimistic; the log sizes are not
affected by load in the same way.

| scale | when | import time | remember p95 | recall p95 | WAL largest at checks / at end |
|---|---|---|---|---|---|
| 100k | before M2 fixes (round 0) | 144.9 s | 47.0 ms | 282.2 ms | up to 4.4 GB (reported) |
| 100k | after M2 fixes | 246.0 s | 148.1 ms (over 50) | 406.4 ms (over 200) | 310 MB / 67 MB |
| 20k | before (shipped build) | 31.2 s | 41.4 ms | 118.0 ms | 533 MB / 546 MB |
| 20k control, loaded machine | after M2 fixes | 41.0 s | 68.3 ms (over 50) | 154.0 ms | 67 MB / 67 MB |

Reading: the log now stays small (310 MB peak at 100k, 67 MB at 20k, and it is back to 67 MB at the end), so the
M2 checkpoint policy does what it was meant to do. The 100k latency budgets are still missed, and remember p95 looks
worse than before, but the run cannot separate the cost of the new writer policy (queued writes first, WAL
checkpoints) from the machine load. A fair verdict needs the same run on a quiet machine; it was not repeated.

### Re-check on a quieter machine (2026-10-15, HEAD 7f338d6, includes M2 c6535e4)

Same command, run once: `ALICE_TEST_BULK=100000 env -u TYPESAFE_API_KEY nice -n 15 cargo test --release -p alice-daemon
--test import_concurrency twenty_clients -j 4 -- --nocapture`. Load average (1 min) at start: 4.94 (below the 6 gate).
Sampled every 30 s during the run (7 samples): 4.94, 6.02, 8.25, 8.47, 15.21, 13.36, 12.01; **max 15.21**. The load
never stayed under 6 once the run was going. Part of that is the bench itself (20 client threads plus the import and
embedding worker on 14 cores), and OrbStack was using about 19% of a core; no other heavy job was started by this run.
So this is not the clean quiet-machine figure that was asked for, and is reported as **inconclusive on latency**.

| scale | when | import time | remember p95 | recall p95 | WAL largest at checks / at end |
|---|---|---|---|---|---|
| 100k | after M2 fixes, load 13-14 | 246.0 s | 148.1 ms | 406.4 ms | 310 MB / 67 MB |
| 100k | 2026-10-15 re-check, start load 4.94, max 15.21 | 153.8 s | 60.5 ms (over 50) | 310.0 ms (over 200) | 525 MB / 67 MB |

Budgets: remember p95 < 50 ms: **FAIL** (60.5 ms); recall p95 < 200 ms: **FAIL** (310.0 ms). 18,997 remembers and
recalls. The test panicked on the remember budget (exit 101). Compared with the loaded run the latencies are much
lower (60.5 against 148.1, 310.0 against 406.4) and the import is faster (153.8 s against 246.0 s); compared with the
pre-M2 figures (47.0 / 282.2 ms, 144.9 s) they are not better. The log peak was 525 MB at the checks (310 MB in the loaded

threads is not separated by this run. Bench homes are tempdirs and were removed; nothing else was changed.

## Gold-set quality: Alice against MemPalace (Task 18)

The first table and the first findings below are the figures **before the M2 ranking fix**; the re-run is at the end of this section.

Synthetic corpus (`tests/data/gold_corpus.json`, 170 drawers, 48 queries, frozen, sha1 b451c963...). Alice: the
corpus as a MemPalace `sqlite_exact` palace, imported, local e5 model (`multilingual-e5-small-q8`), `recall` with
`include_raw`, 10 results. MemPalace 3.10.0: the same drawers in a throwaway palace (`sqlite_exact`, default
`minilm` embedder, hybrid search, `search_memories` top 10), recorded by `scripts/m3_mempalace_baseline.py`. Both are

## Real-query quality on a snapshot of the owner's palace (Task 19 step 6)

80 queries mined from the owner's own past `mempalace_search` calls (local Claude Code transcripts, read-only; deduplicated, trivial ones dropped, seed 20261014). Each system's top 10 were pooled (Alice: `recall --raw --json --limit 10` on the real-model home; MemPalace: its own `search_memories` v3.10.0 against the copy). Candidates were shuffled, stripped of system names and ids, truncated to 1,200 characters of Alice's stored (redacted) text, and graded 0/1/2 by one Claude subagent that saw only the query and the candidates. nDCG@10 uses the pooled grades for the ideal ranking; recall@10 counts pooled candidates with grade >= 1. Paired bootstrap over queries: 10,000 resamples, seed 20261014. Queries, texts and grades are not committed.

| | Alice | MemPalace | Alice − MemPalace (95% interval) |
|---|---|---|---|
| nDCG@10 (80 queries) | 0.610 | 0.693 | −0.083 (−0.147 … −0.018) |
| recall@10 (80 queries) | 0.515 | 0.614 | −0.099 (−0.158 … −0.035) |

Result as measured: on the owner's real queries Alice does **not** beat MemPalace; both intervals are below zero. Nothing was tuned after seeing it.

Caveats: the real-model home embedded only the knowledge tier and the earliest ~5,100 raw chunks (the rest are lexical-only), so Alice's raw-tier recall is understated (50 of Alice's 800 pooled hits are raw chunks); the pool contains only the two systems' top-10, so recall is relative to it; a single grader; the 1,200-character truncation; 128 of 1,467 candidates were returned by both systems; grading text is Alice's stored text, so a MemPalace hit is judged on the imported (redacted) version.
