# M3 benchmarks (import and compatibility)

**100k: MISS** (recall p95 ~300 ms vs the 200 ms budget with 20 constantly-reading clients; cause: unbounded WAL in the M2 store, inferred from the evidence below and not proven; needs an M2 checkpoint policy - escalated). 20k and 30k pass both budgets.

Numbers are filled in by Task 19. This page holds what Task 16 measured.

## Import under load

Test: `crates/alice-daemon/tests/import_concurrency.rs`, release build, fake embedder, synthetic palace
(`fixture::synthetic_palace`: 600-900 character chunks, 3% knowledge drawers, 5% repeats), 20 clients that
each loop `remember` (unique text) + `recall` (alternating a client memory and a rare word of the palace)
with a 5 ms pause, until the import ends. Machine: 14 cores, shared with other work, run at `nice -n 15`.
Budgets: remember p95 < 50 ms, recall p95 < 200 ms.

```
ALICE_TEST_BULK=20000  : import 20000 drawers in 30.7s; remember p95 39.9 ms, recall p95 120.7 ms (7566 remembers, 7566 recalls)
ALICE_TEST_BULK=30000  : import 30000 drawers in 44.6s; remember p95 41.7 ms, recall p95 144.2 ms (9604 remembers, 9604 recalls)
ALICE_TEST_BULK=100000 : import 100000 drawers in 144.9s; remember p95 47.0 ms, recall p95 282.2 ms (19643 remembers, 19643 recalls)   <- recall over budget
```

The same 20 clients on the 100,000-drawer database with no import running: remember p95 10.4 ms,
recall p95 128.2 ms. So the 100k recall figure is the import's doing (the import took 49 s alone and 145 s
under load). At the end of the 30k run the write-ahead log was 744 MB: 20 clients always have a reader open,
so SQLite never gets the quiet moment it needs to restart the log. This is the likely cause and has not been
confirmed; the fix would be in the store's checkpoint policy (M2), so it was not changed here.

One-batch test (`one_batch_never_holds_the_writer_longer_than_the_slice_budget`, 100,000 drawers, a probe
`remember` every 5 ms): 4781 probes, longest ack 37.1 ms (budget 150 ms); 6786 batches, largest 200 records
(a `collapsed` batch, which carries no text) and 15,488 bytes of text.

What was changed to get there: import batches close at 50 records or 16 KB (were 200 and 64 KB) and the job
pauses 2 ms after each committed batch. With 200/64 KB batches remember p95 was 65-82 ms at 30k-100k drawers.

## Fix round 1: write-ahead log control

Tried in the import job only (the M2 store is untouched). "WAL" below is the size of the `-wal` file
(`ImportStatus.max_wal_bytes`: largest size seen at the check made every 20 batches). Nothing in
the import job checkpoints now: the attempts gave no benefit, and the shipped build only measures.

Results of the attempts. Rows marked * had an end-of-job TRUNCATE or measured frames in use after a PASSIVE
checkpoint, which are not in the shipped build, so their WAL cells describe those experiments, not the shipped code.

| variant | scale | import time | remember p95 | recall p95 | WAL peak / end |
|---|---|---|---|---|---|
| none (round 0, 200 rec / 64 KB batches, no pause) | 30k | 44.6 s | 41.7 ms | 144.2 ms | - / 744 MB |
| PASSIVE every 20 batches + back-off (25 ms steps above 128 MB, 2 s cap) * | 20k | 89 s | 26.7 ms | 218.8 ms (over) | * / * |
| same * | 30k | 122 s | 26.6 ms | 259.9 ms (over) | * / * |
| PASSIVE only, no back-off * | 20k | 31.5 s | 42.8 ms | 125.0 ms | * / 585 MB |
| same * | 30k | 46.4 s | 44.4 ms | 153.4 ms | * / * |
| same * | 100k | 152.6 s | 50.3 ms (over) | 300.9 ms (over) | * / * |
| batches 100 rec / 32 KB, pause 4 ms (tuning try) * | 100k | 131.3 s | 60.3 ms (over) | 285.6 ms (over) | * / * |
| **shipped build** (50 rec / 16 KB, 2 ms pause, measure only) | 20k | 31.2 s | 41.4 ms | 118.0 ms | 533 MB / 546 MB |

Findings
- Checkpoint attempts gave no benefit: with PASSIVE the 100k recall was 300.9 ms against 282.2 ms before, and
  the log was as big or bigger. Backing off made it worse: with 20 readers always open the log never gets a quiet
  moment, so waiting only lengthens the import, and the log grows with the clients' own commits and the
  embedding worker's for as long as the import lasts.
- A blocking `wal_checkpoint(RESTART)` from a second connection made the M2 writer's own transactions fail
  with `database is locked` within seconds under load. An end-of-job `TRUNCATE` shrank the log but made writes
  issued right after the job fail (8 existing tests failed in a full run). Neither is used.
- The 100k miss stays: recall p95 about 300 ms against 200 ms, while the same clients on the finished 100k
  database with no import measured 128 ms. The no-import WAL size was not taken, so part of the log may come
  from the clients and the embed worker rather than the import. The cause (an unrestarted log under constant
  readers) is inferred; a direct proof would be the same run on a scratch build with `wal_autocheckpoint` or
  `journal_size_limit` set. That lever is the store's checkpoint policy (M2 behaviour), left alone.

## Gold-set quality: Alice against MemPalace (Task 18)

Synthetic corpus (`tests/data/gold_corpus.json`, 170 drawers, 48 queries, frozen, sha1 b451c963...). Alice: the
corpus as a MemPalace `sqlite_exact` palace, imported, local e5 model (`multilingual-e5-small-q8`), `recall` with
`include_raw`, 10 results. MemPalace 3.10.0: the same drawers in a throwaway palace (`sqlite_exact`, default
`minilm` embedder, hybrid search, `search_memories` top 10), recorded by `scripts/m3_mempalace_baseline.py`. Both are
scored by the same code: exact-duplicate drawers form one group (counted once, labels merged), nDCG@10 with the
ideal ranking from the query's labels, recall@10 over relevant groups. Test:
`cargo test -p alice-daemon --test import_quality -- --ignored --nocapture alice_beats_mempalace_on_the_gold_set`.

**Result: Alice does NOT beat MemPalace on this set** (overall nDCG@10 0.645 against 0.806, recall@10 0.802
against 0.865). The test fails as written; nothing was tuned or edited after seeing this.
