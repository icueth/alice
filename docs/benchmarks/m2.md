# Alice M2 benchmarks

Measured on 2026-10-14 with `alice bench` (`crates/alice/src/bench.rs`), release builds on
`feat/m2-judge-settings`. This file starts with M2 Task 1 (memory budget I): a real-model
measurement mode at 1M chunks, and the raw chunks' vectors moved from an int8 HNSW to a flat
sign-bit index rescored from the f16 vectors in SQLite. Task 2 continues the memory work.

| | |
|---|---|
| Machine | Apple M4 Pro (10 performance + 4 efficiency cores), 24 GB RAM, macOS 26.6.2 |
| Toolchain | Rust 1.99.0, `--release` (thin LTO), SQLite 3.53.2 (bundled), usearch 2.26.4, fastembed 7.1.1 |
| Load | Shared with other agents' work: load average 10–30 during the M1-index run, 11–15 during the sign-bit run. Each run alone, under `nice -n 15`. |

## Real-model runs at 1M chunks: `--prefill-vectors`

Embedding 1M chunks with the local model takes hours, so M1 measured its 1M figures with the
fake embedder and projected the model's share. `alice bench --real --prefill-vectors` writes the
chunk and memory vectors with the fake embedder relabelled as the real model (same id, same 384
dimensions: a vector costs the same in the index whatever its values), then starts a real
`alice daemon run` that loads the real model, embeds 256 new memories through the API and
serves the four bursts of 64 concurrent recalls. The report adds `daemon.remembered`,
`daemon.embed_new_ms` and RSS and footprint after that embedding. In-process latency figures
use fake query vectors; the embedder-alone throughput still measures the real model. Data
written this way is marked `multilingual-e5-small-q8+prefill` and is refused by the other modes.

```
# M1 index (the bench change of this task, before the new index), then the same data with it
alice bench --real --prefill-vectors --chunks 1000000 --memories 10000 --dir <data> --out base-1m.json
alice bench --real --prefill-vectors --chunks 1000000 --memories 10000 --dir <data> --out bq-1m.json
```

The second run reuses the database (1,000,000 chunks, 10,456 memories after the first run's
writes); at start it finds no `chunks.bq`, rebuilds the index from the stored vectors and, on
its first save, deletes the M1 `chunks.usearch`.

## Daemon memory at 1M chunks with the real model

| | M1 (int8 HNSW chunks) | sign-bit chunks |
|---|---|---|
| RSS after start | 754 MB | 842 MB |
| RSS after embedding 256 memories | 662 MB | 722 MB |
| RSS after bursts | 916 MB | 550 MB |
| **Peak RSS** | **953 MB** | **943 MB** |
| Footprint after start | 1,333 MB | 753 MB |
| Footprint after embedding 256 memories | 1,378 MB | 833 MB |
| Footprint after bursts | 1,397 MB | 861 MB |
| **Peak footprint** | **1,397 MB** | **861 MB** |
| Index files | 508 MB chunks + 5.3 MB memories | 53.4 MB chunks + 5.5 MB memories |
| Chunk index rebuild (`VectorIndex::rebuild_from`, both parts) | 333.1 s | 4.4 s |
| Index open | 379 ms | 13.5 ms |
| `recall` p95 (knowledge tier) | 13.5 ms | 10.1 ms |
| `recall` `include_raw` p95 | 108 ms | 150 ms |

MB here are 2^20 bytes, as the bench reports them. The physical footprint fell by 536 MB at
peak (1,397 → 861 MB): the chunk part went from ~510 bytes per vector in RAM to 56 (48 of
code, 8 of key). Peak RSS did not move (953 → 943 MB). RSS counts resident pages only, and in
the M1 run macOS compressed hundreds of MB of the idle HNSW (RSS after embedding 662 MB against
a 1,378 MB footprint), which kept its RSS low. RSS also counts pages the footprint leaves out:
`vmmap -summary` on the sign-bit daemon at 1M (after start and three recalls; footprint 752
MB, peak 844 MB) showed 167 MB of resident `__TEXT` (clean code pages of the binary and system
libraries) and 233 MB resident in freed allocator regions (`MALLOC_SMALL (empty)`, 70 MB of
them dirty), which is why its RSS after start (842 MB) is above its footprint (753 MB). The
800 MB budget is still missed on both measures: one model instance is ~600 MB of the 861 MB
footprint, and the footprint peaks during start-up, while the model loads. Task 2 takes that
on.

## Latency at 1M chunks

In process, one call at a time, 200 samples per query (fake query vectors; p50 / p95 in ms):

| Query | M1 (int8 HNSW chunks) | sign-bit chunks |
|---|---|---|
| `remember` | 3.33 / 9.87 | 3.35 / 9.50 |
| `recall` (knowledge tier) | 5.72 / 13.5 | 5.23 / 10.1 |
| `include_raw` | 24.0 / 108 | 33.5 / 150 |
| ... date filter (k = 400) | 33.1 / 112 | 77.6 / 173 |
| ... rare Thai word | 8.01 / 15.3 | 16.5 / 31.6 |
| ... rare identifier | 41.7 / 57.8 | 53.4 / 157 |
| ... dotted name of twelve common words | 87.3 / 110 | 91.8 / 140 |
| raw fallback | 15.0 / 29.8 | 30.8 / 100 |
| `context` | 0.29 / 0.78 | 0.30 / 0.59 |
| Daemon bursts (4 × 64 concurrent, over HTTP) | 399 / 735 (max 797) | 404 / 794 (max 879) |

Every figure stays within the 200 ms budget, but the raw tier's margin shrank. The scan is not
the cost: ranking 1M codes takes 2.3 ms (p50; 2.8 ms p95). The cost is the rescoring reads:
`search_chunks` reads `k × 4` stored vectors (400 for k = 100, 1,600 under a filter, where
k = 400), each a primary-key lookup and a row lookup in a 2.7 GB database. Measured on the 1M
data, the first sets of 400 random rows on a fresh connection took ~70 ms (p50), and 13–20 ms
once the connection's page cache held the B-trees' interior pages (~35 µs per row; reading
them in seq order made no difference); a whole `search_chunks` whose 400 rows are cached
takes ~3.5 ms. A pooled reader in a running daemon is the warm case, so a raw-tier recall pays
~15–20 ms for 400 candidates and ~50–80 ms for 1,600, which matches the p50 increases above
(+10 ms `include_raw`, +44 ms under a filter). Possible follow-ups if the margin matters:
rescore `max(k, MIN_RESCORE)` candidates when k is already large (the filtered case), or store
`embeddings` as a `WITHOUT ROWID` table (one B-tree descent per row instead of two).

## Start-up

- **Index open:** 13.5 ms at 1M (56 MB of codes and seqs read in 64 KB pieces), from 379 ms.
- **Rebuild:** 4.4 s at 1M for both parts (1,000,000 chunk codes and the 10,656-memory HNSW),
  from 333 s for the int8 HNSW. It runs when an index file is missing, damaged or out of date
  (including the first start after M1, which has no `chunks.bq`); a crash while embedding now
  costs seconds of word-only search instead of five minutes.
- **`embeddings::count`:** 174 ms (1.5 s in the M1-index run: cold OS cache).

## Chunk recall of the sign-bit index

`crates/alice-embed/tests/binary_chunk_recall.rs` (ignored; real model): passages are lines of
40–400 characters from this repository (Rust code first, then English and Thai docs), queries
the first 60% of every 20th passage (300 queries), and the ground truth the exact cosine top 10
over all passages. Recall@10 is the share of it that `search_chunks_with(k = 10)` returns; with
k = 10 the candidate count is `MIN_RESCORE` up to an oversampling factor of `MIN_RESCORE / 10`.

| Candidates rescored | recall@10, 6,000 passages |
|---|---|
| 200 | 0.9703 (first run), 0.9670 (after this task's edits changed the passages) |
| 400 | 0.9853–0.9873 |
| 800 | 0.9933–0.9963 |
| 1,600 | 0.9980–0.9997 |

**Decision: `MIN_RESCORE` = 400** (the plan's rule: if 200 candidates keep less than 0.97,
take the smallest of 400, 800 and 1,600 that does). The test asserts recall@10 ≥ 0.97 at
`CHUNK_OVERSAMPLE` (final run: 0.9850). Recall itself is unaffected: it asks for k = 100, so it
rescored 400 candidates before the change too. The list the raw tier uses (k = 100, 400
candidates) holds 0.9860 of the exact top 10 at 6,000 passages. Both gold tests pass with
their thresholds unchanged (`real_search_quality`: MRR 1.000, every gold pair ≥ 0.82, no
unrelated pair; `search_quality`: MRR 0.962).

**Encodings tried.** The bits are the signs of the centred vector's own coordinates. Two
variants with the same 48 bytes per vector were measured on the same 6,000 passages, 200
candidates: signs of a seeded random ±1 projection of the centred vector (random-hyperplane
hashing) kept 0.944, and the same after dividing each coordinate by its standard deviation
0.934, against 0.970 for the plain signs. On the fake embedder's sparse vectors (~43 of 384
coordinates set) the projection was far better (0.996 against 0.732), which is why the unit
test on fake vectors reads 1,600 candidates, but the real model decides.

**More passages.** The gate's 6,000 passages are far fewer than 1M chunks, and sign bits find
the exact neighbours less often as the corpus grows. With the passages extended from the
`.rs` and `.md` files of the local cargo registry (`ALICE_RECALL_PASSAGES`,
`ALICE_RECALL_EXTRA_DIR`):

| Passages | 400 candidates (`MIN_RESCORE`; the raw tier's k = 100) | 800 | 1,600 |
|---|---|---|---|
| 6,000 (this repository) | 0.985 | 0.993 | 0.998 |
| 24,000 | 0.969 | 0.988 | 0.995 |
| 96,000 | 0.954 | 0.977 | 0.987 |

Each fourfold growth costs ~0.015 at 400 candidates; carried on at that rate, ~0.93 at 1M
chunks (not measured: 1M real-model embeddings take hours). The vector list is one of the raw
tier's fused lists, beside the word, identifier and trigram lists, and M1 never measured its
int8 HNSW's recall at 1M either. More candidates buy recall back at ~35 µs each (see
[Latency](#latency-at-1m-chunks)).
