# Alice M2 benchmarks

Measured on 2026-10-14 with `alice bench` (`crates/alice/src/bench.rs`), release builds on
`feat/m2-judge-settings`. This file starts with M2 Task 1 (memory budget I): a real-model
measurement mode at 1M chunks, and the raw chunks' vectors moved from an int8 HNSW to a flat
sign-bit index whose shortlist is re-ranked in RAM and then rescored from the f16 vectors in
SQLite. Task 2 (memory budget II) runs the embedding model on ONNX Runtime directly, with a
compact tokenizer, the CPU arena off and an idle unload, and meets the 800 MB budget at 1M
chunks. Task 3 builds usearch without NumKong so that Windows links, and measures what that
costs (the [Windows](#windows-task-3) section). Task 6 (live settings) measures the idle unload
in the daemon, ONNX Runtime's threads and spinning, and the macOS allocator cache (the last
section).

## Real-model runs at 1M chunks: `--prefill-vectors`

Embedding 1M chunks with the local model takes hours, so M1 measured its 1M figures with the
fake embedder and projected the model's share. `alice bench --real --prefill-vectors` writes the
chunk and memory vectors with the fake embedder relabelled as the real model (same id, same 384
dimensions: a vector costs the same in the index whatever its values), then starts a real
`alice daemon run` that loads the real model, embeds 256 new memories through the API (8 of
them twelve sentences long, past the model's 512-token window, so ONNX Runtime's arena grows
as it would with transcript-sized text) and serves the four bursts of 64 concurrent recalls.
The wait for that embedding fails the bench after 600 s with the daemon log's path. Every text
the bench writes carries the run's number, so on reused data nothing is a duplicate (a
duplicate is acknowledged without being stored or embedded). The report adds
`daemon.remembered`, `daemon.remembered_long`, `daemon.embed_new_ms` and RSS and footprint
after that embedding. In-process latency figures use fake query vectors; the embedder-alone
throughput still measures the real model. Data written this way is marked
`multilingual-e5-small-q8+prefill` and is refused by the other modes.

```
# M1 index (the bench change of this task, before the new index), then the same data with it
alice bench --real --prefill-vectors --chunks 1000000 --memories 10000 --dir <data> --out base-1m.json
alice bench --real --prefill-vectors --chunks 1000000 --memories 10000 --dir <data> --out bq-1m.json
```

The second run reuses the database (1,000,000 chunks, 10,456 memories after the first run's
writes); at start it finds no `chunks.bq`, rebuilds the index from the stored vectors and, on
its first save, deletes the M1 `chunks.usearch`.

In these runs the 200 ms budget was missed by `include_raw` in two of three (212 and 239 ms;
161 ms in the first), and by the first version too in the later environment (filtered 308 ms,
`include_raw` 204 ms). Fix round 2 (next section) brought it back. What each part costs at
1M, measured on this data:

- **Rows read from SQLite.** `search_chunks` now reads `max(k, MIN_RESCORE)` rows: 400 for
  k = 100 and 400 under a filter (k = 400; the first version read 1,600 there, hence the
  filtered gain). A row is a primary-key lookup plus a row lookup in a 2.7 GB database: ~35 µs
  each once a connection's page cache holds the B-trees' interior pages (13–20 ms for 400), up
  to ~170 µs on a fresh connection (~70 ms for 400). Reading in seq order made no difference.
- **In RAM.** Two scans of the 1M codes (a distance histogram fixes the shortlist's cut, then
  the shortlist is collected; ~4.6 ms) and the re-rank of the 32,000-code shortlist against the
  float query: ~9 ms in all (p50; a bounded heap took 15 ms for this shortlist). The first
  version's single heap scan for 400 codes took 2.3 ms.
- **Why the first version looked faster here.** The bench's chunks and queries are fake,
  sparse vectors whose codes tie often, and ties go to the older seq: over 50 bench-like
  queries the first version's 400 Hamming candidates covered only 3,277 distinct rows (each
  read ~6 times, so mostly cached), the re-ranked 400 covered 6,754. Real queries read mostly
  distinct rows either way, so the first version's raw-tier figures were optimistic, and the
  re-rank's genuine extra cost is the ~7 ms in RAM.
- **Cold file cache.** A measurement with the OS file cache emptied (`purge`) needs sudo, which
  this environment does not have; the A/B columns show a partly cold cache.

### The chunk vector list beside the word lists (fix round 2)

A raw-tier recall used to run its lists one after the other on its reader: the word, code and
trigram lists (~100–170 ms at p95 at 1M since M1), then the chunk vector list (~9 ms in RAM and
400 SQLite reads). Now the chunk vector list runs on a thread of its own with a connection of
a separate small pool (`ServiceOptions::vector_reader_pool`: 4 read-only connections, 4 MiB
page cache each), started as soon as the raw tier is known to be needed (at once for
`include_raw`, so it also overlaps the knowledge tier; after the knowledge tier for the raw
fallback), and joined when the word lists are done: the raw tier takes as long as the slower
of the two. A recall takes one main reader and then at most one vector reader, never a second
of either, so the pools cannot deadlock (tested with 2 main readers, 1 vector reader and 16
concurrent `include_raw` recalls; drawing the vector reads from the main pool instead
deadlocks that test). A failure in the vector part leaves the word matches, as before. The
results are those of the one-connection search (tested).

## Start-up

- **Index open:** 13–15 ms at 1M (56 MB of codes and seqs read in 64 KB pieces), from 379 ms.
- **Rebuild:** 6.2 s at 1M for both parts (1,000,000 chunk codes and the ~11,000-memory HNSW;
  4.4 s for the first version, which did not sample), from 333 s for the int8 HNSW. The chunk
  part is built in one go: its mean fitted on 4,096 stored vectors spread evenly over all chunk
  seqs (one index seek each), every code appended as read, and the codes sorted by seq once.
  A rebuild runs when an index file is missing, damaged or out of date (including the first
  start after M1, which has no `chunks.bq`).
- **Unclean stops.** A clean stop saves the index and leaves `vectors/<model>.clean`; a start
  takes the mark. Without it (a crash, say while embedding) the chunk part is rebuilt from the
  stored vectors even when the counts agree (it can miss chunks or hold stale ones), and the
  whole index if they still disagree afterwards: seconds of word-only search at 1M.
- **`embeddings::count`:** 174 ms with a warm file cache (0.4–1.5 s cold).

## Chunk recall of the sign-bit index

**How it ranks.** `search_chunks(k)` (1) takes the `max(4,000, 32·√N)` codes nearest to the
query by Hamming distance, (2) re-scores them in RAM against the float query,
`Σ (q_i − mean_i) · (bit_i ? 1 : −1)` (no extra memory), and (3) reads the best
`max(k, MIN_RESCORE)` of those from SQLite and rescores them by exact cosine. The bits are the
signs of the centred vector's own coordinates.

**The gate.** `crates/alice-embed/tests/binary_chunk_recall.rs` (ignored; real model).
Passages are lines of 40–400 characters, first from this repository (Rust code, then English
and Thai docs; ~13,500 lines), then from the `.rs` and `.md` files under
`ALICE_RECALL_EXTRA_DIR` (here the local cargo registry, `~/.cargo/registry/src`). For each
corpus size the queries are the first 60% of every (size / 300)th passage (300 queries) and the
ground truth is the exact cosine top 10 over the corpus. Recall@10 is the share of it that
`search_chunks(k = 10)` returns, measured on an index filled by inserts (live: mean of the
first 4,096 vectors) and on one rebuilt from the table (mean of a sample spread over all
chunks). The test asserts recall@10 ≥ 0.97 at every size; the default run is the 6,000-passage
smoke test, `ALICE_RECALL_EXTRA_DIR=~/.cargo/registry/src` adds 24,000 and 96,000.

| Passages | recall@10 (`MIN_RESCORE` = 400) | 100 rows | 200 rows | 800 rows | without the re-rank (400 rows) | raw tier's list (k = 100) |
|---|---|---|---|---|---|---|
| 6,000 | 0.998 live · 0.998 rebuilt | 0.972 · 0.974 | 0.992 · 0.993 | 1.000 · 0.999 | 0.987 · 0.986 | 0.999 · 0.998 |
| 24,000 | 0.993 · 0.995 | 0.958 · 0.964 | 0.980 · 0.985 | 0.998 · 0.999 | 0.969 · 0.974 | 0.993 · 0.995 |
| 96,000 | 0.987 · 0.991 | 0.953 · 0.955 | 0.971 · 0.979 | 0.997 · 0.995 | 0.964 · 0.969 | 0.987 · 0.992 |

The passages include this repository's own files, so they change with every edit: an earlier
run of the same test (a few edits before) measured 0.980 / 0.984 at 96,000 with 400 rows and
0.963 / 0.965 with 200; differences of up to ~0.008 between runs are this noise.

**Decisions.**
- `MIN_RESCORE` = 400, by the plan's rule measured at scale: the smallest of 200, 400, 800 and
  1,600 rows that keeps recall@10 ≥ 0.97 at 96,000 passages, live and rebuilt (200 kept 0.963
  in one of the two runs).
- Shortlist `max(4,000, 32·√N)` (24k: 4,960; 96k: 9,920; 1M: 32,000). In a sweep over cached
  embeddings of the same 96,000 passages, recall with 400 rows rose from a 1,000 to a 4,000
  shortlist (0.985 → 0.991) and by at most 0.002 beyond 8,000; at 1M a 32,000 shortlist costs
  ~9 ms in RAM.

**Extrapolation to 1M (not measured: embedding 1M real passages takes hours).** Recall@10 is
taken as linear in log₄ N, with the slope of the 24,000 → 96,000 step, and carried on
log₄(1,000,000 / 96,000) = 1.69 steps:

| | 24k → 96k slope per fourfold | 1M, extrapolated |
|---|---|---|
| live, this run | −0.006 | 0.977 |
| rebuilt, this run | −0.003 | 0.986 |
| live, earlier run (0.988 → 0.980) | −0.008 | 0.967 |

So the re-rank holds recall@10 near or above 0.97 at 1M on this extrapolation, where the
Hamming-only first version (0.985 → 0.969 → 0.954 at 6k / 24k / 96k with 400 rows) fell to
~0.93. A live index whose first 4,096 chunks are unlike the rest is the weak case (its mean is
fixed by them); a rebuild, including the one after every unclean stop, refits the mean on the
whole corpus. 800 rows would hold 0.995–0.997 at 96,000 passages, at ~14 ms more per raw-tier
recall.

**Encodings tried (first version, 6,000 passages, 200 rows, Hamming only).** Signs of a
seeded random ±1 projection of the centred vector kept 0.944, the same after dividing each
coordinate by its standard deviation 0.934, against 0.970 for the plain signs.

**Unit test fixture.** `bq.rs` tests use seeded dense vectors that share one strong direction
(vectors of different clusters at cosine ~0.81, like unrelated e5 texts at ~0.7): centred
bits keep 1.00 of the exact top 10 within 200 Hamming candidates, uncentred bits 0.45.

Both gold tests pass with their thresholds unchanged (`real_search_quality`: MRR 1.000, every
gold pair ≥ 0.82, no unrelated pair; `search_quality`: MRR 0.962).

## Task 2: the embedding model on ONNX Runtime directly

**Daemon RSS < 800 MB at 1M chunks: met (peak 580–601 MB RSS, 558–588 MB footprint).** Two
runs of `alice bench --real --prefill-vectors --chunks 1000000 --memories 10000` on the
same data, with no fallback step needed: the SQLite caches and ONNX Runtime's thread count are
unchanged.

`alice_embed::OnnxEmbedder` replaces fastembed in the daemon and the bench: one ONNX Runtime
session (`ort` 2.0.0-rc.13, the version fastembed linked) with graph optimization level 3, the
CPU arena and memory patterns off, and the model read from its file by ONNX Runtime;
`alice_embed::tokenizer::UnigramTokenizer` instead of the Hugging Face `tokenizers` crate;
mean pooling over the attention mask and L2 normalisation as before. With
`OnnxOptions::idle_unload` (10 minutes in the daemon; a setting from Task 6) the session is
dropped after that long unused and reloaded on demand: a query that arrives meanwhile is not
held up (it uses the word lists and starts the reload in the background), the embedding
worker waits for the reload. fastembed remains a dev-dependency of the equivalence test only.

### Same vectors as M1

`crates/alice-embed/tests/onnx_equivalence.rs` (ignored; real model):

- **Token ids: 0 mismatches over 823 texts** (1,640 encodings: each text with the `passage: `
  and the `query: ` prefix, and six without one: empty text, spaces only, text the normalizer
  removes whole): edge cases (runs of spaces, tabs and newlines, Thai without spaces,
  fullwidth text and ligatures that the normalizer rewrites, emoji, combining marks,
  private-use, zero-width and control characters, no-break and ideographic spaces, a literal
  `▁`, 4,000-character and 2,100-character texts cut at 512 tokens) and every line of the
  READMEs and the core spec. A `tokenizer.json` whose pipeline differs from the one
  implemented (normalizer, Metaspace pre-tokenizer, `<s> … </s>` post-processor, byte
  fallback, added tokens) is refused with the next step instead of being tokenized
  differently.
- **Vectors: worst cosine 1.000000** over 200 passages embedded in the batches M1 ran
  (`passage_batches`, 19 calls), 1.000000 with each passage alone, 1.000000 over 20 queries.
  The int8 model quantizes its activations per call (48 `DynamicQuantizeLinear` nodes: one
  scale for the whole batch, padding included), so a vector depends slightly on the texts
  batched with it: fastembed's own batches of 8 give a worst cosine of 0.99911 against the
  same passages in M1's batches. Batches are padded with `config.json`'s `pad_token_id` (0),
  as fastembed did; padding with `<pad>` (1) instead moved the worst cosine to 0.99926.

Stored M1 vectors therefore stay valid, and the model id stays `multilingual-e5-small-q8`, with
one exception: text containing a special token's literal text (`<s>`, `</s>`, `<pad>`, `<unk>`,
`<mask>`) is now tokenized as text, where Hugging Face, and so M1, emitted the special id.
Such a stored vector differs slightly from what the text embeds to now; it stays usable, and
the text's next re-embedding replaces it.

### What each change saved

The model alone in a process (`vmmap -summary`), loaded and then after embedding 64 passages
(16 of them past 512 tokens) in M1's batches:

| | loaded | after embedding | peak |
|---|---|---|---|
| fastembed 7.1.1 (M1) | 600 MB | 742 MB | 843 MB |
| ONNX Runtime + compact tokenizer, arena and memory patterns on | 348 MB | 413 MB | 413 MB |
| **ONNX Runtime + compact tokenizer, arena and memory patterns off** (shipped) | **348 MB** | **307 MB** | **427 MB** |
| the compact tokenizer alone | 47 MB (21 MB live) | | |

- **Sign-bit chunk index (Task 1):** peak footprint at 1M 1,397 → 861–887 MB.
- **Compact tokenizer:** ~250 MB. One hash map of the 250k pieces (~21 MB live) instead of the
  `tokenizers` trie with a hash map per node: the loaded model fell from 600 to 348 MB.
- **CPU arena and memory patterns off:** ~105 MB after embedding (413 → 307 MB). With the
  arena ONNX Runtime keeps its largest call's working memory for good; without it the memory
  goes back to the allocator after each call. Query latency is unchanged: 600 alternating
  single queries on both sessions gave p50 4.45 / 4.46 ms and p95 5.91 / 5.92 ms.
- **In the daemon at 1M:** peak footprint 867–888 → 558–588 MB, peak RSS 815–973 → 580–601 MB.
- **Fallback steps** (`READER_CACHE_KIB` 8 MiB, `WRITER_CACHE_KIB` 32 MiB, 4 ONNX Runtime
  threads): none applied, none needed.

**Allocator caching on macOS.** About 210 MB of the 348 MB "loaded" figure is memory freed
while ONNX Runtime builds the session (the parsed model file, graph optimization) that macOS's
allocator keeps in its cache of large blocks: `MALLOC_LARGE (empty)` regions, resident and
dirty, so counted in the footprint. With `MallocLargeCache=0` (or `MallocSpaceEfficient=1`) in
the environment the loaded model is 136 MB and the arena-off session 163 MB after embedding.
The same cache limits what an idle unload gives back (below). Both variables are read by the
allocator at process start, so using one means setting it in the daemon's environment when it
is launched; that is not done here (Task 6 measured it: see below, and did not set it).

### Idle unload

Unit tests (`alice-embed/src/lazy.rs`, no model) cover the reaper, the background reload for
queries, the blocking load for passages, a loader thread that cannot start (reported, retried
by the next query), loads never running twice at once (a waiting caller reuses a background
load instead of building a second copy), a query not waiting while the worker loads, a reload
waiting until the reaper has freed the old session (the reaper frees it under the load lock),
a loader that panics not blocking later reloads, and `is_loaded` answering while a batch runs.
A query that falls back because the model is reloading is logged at debug level (other
embedding failures stay warnings). With
the real model (`tests/real_model.rs`, 500 ms idle time): the session is dropped, a query then
fails at once with `MODEL_LOADING` and starts the reload (79 ms with the file in the OS
cache), passages wait for it, and the vectors before and after are identical.

In a real daemon (`alice daemon start` on a fresh home, 600 s idle time, one memory):
- The unload was logged 615 s after the last recall (600 s plus the reaper's 30 s tick).
- The next recall returned in 43 ms with `matched: words` (the log says why), and the one two
  seconds later matched `vector+words`.
- Footprint 356 MB before → 163 MB unloaded → 310 MB reloaded. RSS is not comparable there:
  macOS had compressed the idle daemon's pages (32 MB resident).

In a process holding only the model, with the default allocator, the unload gave back less:
footprint 421 → 357 MB (live large blocks 110 → 18 MB, but 206 MB of freed large blocks stayed
cached) and RSS did not move. With `MallocLargeCache=0` it went 135 → 40 MB. The saving in
the daemon at 1M is measured in Task 6, when the idle time is a setting.

### Search quality with the new embedder

- `real_search_quality` (gold set): MRR 1.000, 13 / 13 in the top 3, every gold pair ≥ 0.841
  and every unrelated pair ≤ 0.771 as the int8 index reports them, the raw fallback fired 6 /
  6: the figures of M1.
- New in this task, ten queries that share no word with their memory (a fixture check confirms
  that only the vector list reaches them): five cross-lingual (four Thai queries for English
  memories, one English query for a Thai memory) and five English paraphrases. Their
  similarity (int8) is 0.726–0.859; **six of the ten are below the 0.82 relevance floor and
  are not returned at all** (a result needs a lexical match or a similarity at or above the
  floor), and the three lowest (0.726, 0.759, 0.767) are below the highest unrelated pair
  (0.771), so no floor separates the two sets. The four above the floor are ranked 1–2; with
  no floor, 8 of the 10 rank their memory in the top 3. Since the vectors are M1's, this was
  already so in M1. The test pins each query's outcome at the default floor (the four
  returned in the top 3, the six not returned, so a change of floor policy or model must
  update the table and this page) and asserts that at least 8 of the 10 are in the top 3
  with no floor. The floor policy for such queries is Task 13's. Since Task 3 the two rows

## Windows (Task 3)

**The build links on Windows.** usearch 2.26.4's default `numkong` feature makes its C++ refer
to the NumKong SIMD kernels through `__declspec(dllimport)` names that the static NumKong
library does not provide under MSVC (`LNK2019: __imp_nk_capabilities` and four more). With
`usearch = { version = "2.26.4", default-features = false }` usearch compiles its own portable
distance code (`USEARCH_USE_NUMKONG=0`) and NumKong is not built at all, on every OS. Since
Task 1, usearch holds only the memory vectors (the chunks are the sign-bit index, plain Rust),
so the slower kernels touch only the memory search and the memory HNSW's inserts.

**Index files under any directory name.** usearch opens files through C paths, which fail for
names that are not ASCII on Windows (a Thai user name in `ALICE_HOME`) and for names that are
not UTF-8 on Unix (the M1 code refused those with an error). The memory part is now
serialized in memory and its file read and written by Rust (`load_from_buffer` /
`save_to_buffer`, still a temp file, sync and rename); the chunk part was already Rust.
`vector::tests::index_files_save_and_open_under_unusual_directory_names` saves and opens an
index under `ข้อมูล ทดสอบ/vectors` on every OS and, on Linux, under a directory whose name is
not UTF-8 (APFS refuses such names, so on macOS that case is skipped).

**Transient memory of the buffers.** A save serializes the memory part into one buffer of the
file's size before writing it, and an open reads the whole file before usearch copies it into
its own structures, so each briefly holds one extra copy of the memory part. Its file is
0.5–0.7 KB per memory (10.5 MB for 20,800 memories in the bench data below, 6.9 MB for ~10,500
in the 1M runs above; allow 0.8 KB as the HNSW grows), so the extra copy is ~10–16 MB at 20,000
memories and ~100–160 MB at 200,000, released as soon as the save or open is done. The chunk part streams through a `BufWriter`
and a `BufReader` as before.

**Paths on Windows.** `project.rs` strips the `\\?\` (and `\\?\UNC\`) prefix that
`canonicalize` adds on Windows before a path reaches `git -C` or a `path:` key
(`alice_core::project::strip_verbatim`; identity elsewhere). It keeps the verbatim form when the
ordinary one would name another file: a component ending in `.` or a space (Win32 trims them),
a device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, any case, with or
without an extension), 260 UTF-16 units or more, or a verbatim kind other than a drive or UNC
path (`\\?\Volume{…}\`). `path:` keys use `/` and an upper-case drive letter on Windows, the
form git prints, so a plain directory and a repository without a remote at the same place
have the same key (tested on every OS; the pure string checks too).

## Task 6: live settings, the idle unload, ORT threads and spinning

`embedding.idle_unload`, `embedding.batch_size` and `server.port` now come from the settings
(`ALICE_EMBEDDING_IDLE_UNLOAD=30s` below is the environment layer of the same setting). The
three measurements carried from Task 2 follow. The A/B runs use a real daemon (`alice daemon
run`, the release build) on a throwaway home with 20,000 chunks and 2,000 memories made by
`alice bench --real --prefill-vectors`: threads, spinning and the allocator act on the model's
calls, not on the index, so the 1M data is not needed for them. A script (outside the repo)
starts the daemon, sends 10 recalls to load the model, then measures 300 sequential recalls
(each embeds its query), 4 bursts of 64 concurrent recalls, 256 new memories through the API
(8 of them long) until `embed_backlog` is 0, and the daemon's CPU time over a 30 s idle window
(`ps cputime`). Footprint is `footprint -p` (macOS physical footprint). Each configuration ran
3–4 times, rotated so that a drifting load spreads over all of them; the tables show medians.

### Idle unload at 1M chunks (the real model, `ALICE_EMBEDDING_IDLE_UNLOAD=30s`)

`alice daemon run` on the 1M-chunk bench data (throwaway home under the scratch directory),
one recall, 75 s of silence, one more recall:

| | RSS | physical footprint |
|---|---|---|
| loaded (after a recall) | 462 MB | 442 MB |
| after 75 s idle (the log says `unloaded the embedding model after idle time idle_secs=30`) | 32 MB | **182 MB** |
| after the next recall (reloaded) | 292 MB | 462 MB |

- **Spinning.** With the default (on) or off there is no difference in throughput, burst
  latency or CPU (embedding 256 passages: 11.1 vs 10.7, 7.1 vs 7.1 and 6.0 vs 5.9 CPU
  seconds; the 4 bursts: 13–15 CPU seconds either way), and the idle daemon uses 0.0 s of
  CPU in 30 s in both. Off was 1–8% slower on a single query's p95 in the six pairs, but the
  p50 columns do not agree for 4 and 8 threads and the rounds vary by more than that: the
  difference is within noise. **Kept: ONNX Runtime's default (on).**
- **Threads.** Fewer threads answer one query faster: p95 9.2 → 6.8 ms (run 1) and 11.8 → 9.1
  ms (run 2) from 14 to 4 threads, about 25% in both runs (probably because at 14 threads every call
  waits for the slowest of the efficiency cores; that cause was not measured). Embedding the same 256 texts takes 36% less CPU at 4
  threads (7.1 s against 11.1) and 46% less at 2. The price is bulk embedding: 107–112
  passages/s against 133–136, which is 2.3 s instead of 1.9 s for the bench's 256 memories.
  Burst p95 fell with 4 threads in run 1 (278 → 148 ms) and did not in run 2, when the
  machine's load reached 21 (482 → 508): the burst figures are load-bound and are not
  decisive either way. In one in-process run with large batches (the bench's "embedder alone", load 12), 4
  threads embedded 202 passages/s, against 194–203 at 14 threads in Task 2's runs: not a
  same-time A/B. That the cost shows only with the small batches of a trickle of `remember`
  calls is a hypothesis.
- **Decision: `min(4, cores)` intra-op threads**, on every OS, from the one machine above
  (`alice_embed::DEFAULT_INTRA_THREADS`;
  `OnnxOptions::intra_threads` still overrides). A background daemon should answer a query
  quickly and leave the cores to the person's own work; eight threads would keep the full
  embedding rate (137 passages/s) with a query p95 of 8.4 ms if bulk imports ever matter more.
  There is no setting for it (the schema is the spec's).

### macOS `MallocLargeCache=0` (and `MallocSpaceEfficient=1`)

Set in the daemon's environment at spawn, 4 threads, 3 rounds each, `idle_unload` 20 s
(load average 4.4–13.8). Footprint in MB (medians of 3 rounds per run; the default column
spans its two runs, so it shows a range):

| | default | `MallocLargeCache=0` | `MallocSpaceEfficient=1` |
|---|---|---|---|
| loaded (10 recalls) | 383 | **167** | **162** |
| after embedding 256 memories and 10 s idle | 242–264 | 232 | 225 |
| after the idle unload | 249–257 | **111** | **106** |
| after the reload (one recall) | 368–382 | 226 | 214 |
| query p95 (ms) | 11.0–11.2 | 11.3 | 12.3 |
| **passages/s through the API** | **111** | **58** | **63** |

Both variables cut what the loaded model holds (the allocator no longer keeps the freed
build-time blocks) and what an unload gives back: **−216 MB loaded, −140 MB after an idle

free goes back to the system and each allocation faults its pages in again. Once the model has

is: not set in `spawn_detached`.** Task 17 (service files) decides again with this table: the
trade is 140 MB less while idle against half the speed of a bulk import.
